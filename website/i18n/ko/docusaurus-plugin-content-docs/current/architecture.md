# 아키텍처와 개념

> 📚 [문서 홈](./README.md) — 이 페이지는 시스템 개요입니다. 화면 사용법은
> [사용자](user-manual.md)·[관리자](admin-manual.md) 가이드를 보세요.

## 한 문단으로

gShare는 GPU를 직접 나누지 않습니다. 실제 분할은 [HAMi](https://github.com/Project-HAMi/HAMi) —
VRAM과 코어 한도로 묶인 vGPU — 가 하거나, 카드 전체를 넘겨줍니다. gShare는 그 **위의 제어
플레인**입니다. 누가, 무엇을, 얼마 동안, 얼마에 쓰는지 결정합니다. 보통의 Kubernetes + HAMi에 세션
승인, 점유율 기반 과금, 계층적 한도, 유휴 자원 회수를 더해 여러 조직·부서·사용자가 클러스터 하나를
나눠 쓰게 합니다.

## 구성 요소와 흐름

```
  사용자와 관리자
      │  브라우저
      ▼
  콘솔 (frontend, React SPA)             ── 사용자·관리자 화면, REST + SSE
      │  REST / SSE
      ▼
  제어 플레인 (backend, Python/FastAPI)   ── 상태와 돈의 주인: 인증, 인가, 크레딧,
      │   ├ gshare-api    : 승인, CRUD, 토큰 발급           예산, 카탈로그, 정책, 스케줄링
      │   └ gshare-worker : 과금, 예산 집계, 대기열, 리필
      │  GShareSession CR 적용 (kubeconfig 경유)   ▲ 서명된 상태·인벤토리 콜백
      ▼                                          │ (내부 JWT)
  오퍼레이터 (Go, 클러스터당 하나) ──▶ Pod / Service / Ingress / Secret (gshare-sessions)
      │                                  세션 파드 = 인터랙티브 환경
      ▼                                  (VS Code, JupyterLab, 웹 터미널)
  HAMi + GPU 노드                     ── 실제 분할(gpumem / gpucores) 또는 카드 전체

  postgres (상태와 원장) · redis (대기열, 토큰, 락)
```

| 구성 요소 | 언어·위치 | 책임 | 상세 |
|---|---|---|---|
| 콘솔 | React + TypeScript · `frontend/` | REST와 SSE 위의 사용자·관리자 SPA | [frontend/README](../frontend/README.md) |
| 제어 플레인 | Python + FastAPI · `backend/` | 돈과 세션 상태의 권위: 승인, CRUD, 토큰 | [backend/README](../backend/README.md) |
| 오퍼레이터 | Go · `operator/` | `GShareSession` 리소스를 파드·서비스·인그레스로 재조정하고 상태를 보고 | [operator/README](../operator/README.md) |
| GPU 분할 | HAMi(외부) | VRAM·코어로 묶인 vGPU, 또는 전용 카드 | — |

제어 플레인은 클러스터에 무관합니다. 외부 GPU 클러스터에 kubeconfig로 커스텀 리소스를 적용하고, 각
클러스터의 오퍼레이터가 이를 재조정해 **서명된 내부 JWT 콜백**으로 상태와 인벤토리를 답합니다. 돈과
상태에 관한 결정은 제어 플레인에서만 내립니다.

## 핵심 개념

- **오퍼링** — GPU 모델 카탈로그. 카드 전체 모델당 한 행, 시간당 크레딧 단가를 가짐. 세션 생성
  때 선택.
- **프리셋** — 세션 크기 카탈로그: 컴퓨트(CPU, 메모리, 디스크) + GPU 분할 티어(XL ½, L ¼, M ⅛,
  S 1/16) 또는 전용 카드. VRAM과 코어 한도는 오퍼링의 카드 전체 VRAM에 티어 비율을
  적용해 도출.
- **세션** — 파드가 받치는 인터랙티브 작업 환경. 모드는 **공유**(VRAM·코어 일부) 또는
  **전용**(카드 전체). MIG는 세션 모드가 아니라 카드별 풀입니다. 프로파일에 맞는 공유 요청은
  MIG 인스턴스에 투명하게 배치될 수 있습니다.
- **점유율** — `max(VRAM 비율, 코어 비율)`. 과금은 `단가 × 점유율 × 실행 시간`. 전용 세션의
  점유율은 1.0.
- **크레딧, 지갑, 예산** — 크레딧은 지갑 계층(시스템 → 조직 → 부서 → 개인)을 따라 배분되지만,
  세션은 **요청자 본인의 개인 지갑에만** 과금됩니다. 예산은 범위별로 따로 두는 한도 게이트로,
  경고 또는 차단할 수 있습니다.
- **자원 정책** — 동시 세션 수, 총 할당 자원, 유휴 시간 한도. 가장 구체적인 것부터 적용:
  **사용자 → 부서 → 조직 → 전역**.
- **일시정지와 재개** — 일시정지는 파드를 내려 오퍼레이터가 **GPU를 반환**하게 하고(다른 세션이
  즉시 가져갈 수 있음) **컴퓨트 과금을 멈추되**, 세션 자체는 보존합니다. 유지되는 볼륨은 무료.
  재개는 **GPU를 다시 확보**하고 파드를 다시 만듭니다. 유휴 GPU 세션은 정책에 따라 자동
  일시정지될 수 있으며, 그것이 용량을 회수하는 방법입니다.
- **대기열과 우선순위** — 용량이 소진되면 세션은 실패하는 대신 대기열에 들어가고, 자원이 돌아오면
  우선순위 순으로 승인됩니다.
- **볼륨** — 읽기 전용 또는 읽기·쓰기의 영구 개인·부서 스토리지. 공유 가능. **과금하지 않음**:
  스토리지는 크레딧이 아니라 자원 정책의 사용자별·부서별 쿼터로 제한됩니다.
- **RBAC** — `super_admin`(전체), `org_admin`(조직 하나), `group_admin`(부서 하나), `member` /
  `guest`. 사용자 콘솔과 관리자 콘솔은 별개의 화면입니다.
- **CUDA 호환성** — CUDA 버전이 오퍼링의 `min_cuda`보다 낮은 이미지는 거부됩니다.

## 세션 승인

세션 생성 요청은 무엇이 시작되기 전에 다음 게이트를 순서대로 통과해야 합니다.

1. **참조와 CUDA** — 오퍼링, 이미지, 지갑이 존재하고 이미지의 CUDA 버전이 오퍼링을 만족.
2. **마운트 권한** — 요청한 볼륨을 요청한 모드로 접근 가능.
3. **과금 지갑** — 대상 지갑이 요청자 본인의 개인 지갑.
4. **자원 정책 한도** — 동시 실행·총 자원 한도(사용자 → 부서 → 조직 → 전역).
5. **예산 게이트** — 범위 예산. 차단형 예산은 초과 시 거부.
6. **크레딧 예약** — 예상 비용을 잔액에서 예약. 부족하면 거부.
7. **VRAM 예약** — 점유율을 고려한 2차원 best fit으로 카드 선택. 맞는 카드가 없으면
   **대기열**.
8. **오퍼레이터 인계** — 커스텀 리소스 적용, 파드 시작, running 콜백 도착, 과금 시작.

CPU 전용 세션은 무료이며 예산·예약·VRAM·대기열·GPU 단계를 전부 건너뜁니다.

## 무엇이 다른가

분할 메커니즘(HAMi) 위에 gShare는 점유율 기반 배치와 과금, 일시정지를 통한 유휴 GPU 자동 회수,
선점 대여를 동반한 제자리 GPU yield(무손실 인계와 재개), 계층적 한도 관리를 결합합니다.

## 네임스페이스

| 네임스페이스 | 용도 |
|---|---|
| `gshare-system` | 제어 플레인: api, worker, operator, Postgres, Redis, ingress |
| `gshare-sessions` | 테넌트 세션 파드, `restricted` Pod Security Admission 적용 |
| `gshare-infra` | 특권 DaemonSet: node-problem-detector, Spegel, 이미지 프리풀러 |

## 노드별 지표 에이전트(선택)

`gshare-agent`는 각 세션의 cgroup v2 카운터 — cAdvisor가 읽는 것과 같은 `cpu.stat`,
`memory.current` — 를 노드에서 직접 1초마다 읽어 내부 JWT로 제어 플레인에 배치 전송하는
DaemonSet입니다. 샘플은 세션당 5분 링으로 Redis에 있으며 `GET /sessions/{id}/usage/live`로
제공됩니다. 세션 페이지는 DaemonSet이 보고 중이면 CPU·메모리 선에 이를 쓰고, 아니면 Prometheus
시계열로 대체합니다.

존재 이유는 하나입니다. cAdvisor는 약 10초의 자체 하우스키핑 주기로 집계하므로 어떤 수집 주기도
그보다 신선한 값을 줄 수 없습니다. 2 vCPU 부하로 측정하면 에이전트는 약 1초 만에 변화를 보여 주고
지표 파이프라인은 10~30초가 걸립니다.

에이전트는 기본 꺼짐이며, infra 네임스페이스에서 돌고(읽기 전용 `/sys/fs/cgroup` 바인드에 hostPath를
허용하는 네임스페이스가 필요), 특권이 없고, 자기 노드의 파드만 읽습니다. 아무것도 에이전트에
의존하지 않습니다. Prometheus가 기록이고, GPU·호스트 시계열의 유일한 소스이며, 종료 시 기록되는
영구 세션 요약의 소스입니다.
