# 이미지와 템플릿

이미지 카탈로그는 세션 생성 마법사에서 제공하는 추천 이미지 목록입니다. 목록에 없거나 선택한 GPU 카드와 호환되지 않는 이미지는 실행할 수 없습니다.

![이미지](/img/screens/admin-images.png)

| 열 | 의미 |
|---|---|
| **이름** | 사용자에게 표시되는 이미지 이름 |
| **종류** | 카탈로그 이미지 또는 사용자 개인 이미지 |
| **소스** | 레지스트리 참조 경로 |
| **CUDA** | 이미지 내부의 런타임 버전. 오퍼링의 최소 요구 버전과 비교하여 호환성을 검증합니다. |
| **지원 GPU** | 검증된 GPU 모델 목록 |
| **공개** | 전체 공개 또는 소유자 전용(비공개) 여부. 해당 행에서 설정 상태를 전환합니다. |

탭은 **카탈로그**와 **빌드** 두 가지로 구성됩니다. **빌드** 탭에서는 빌드 성공 여부와 관계없이 콘솔에서 실행된 모든 빌드의 상태와 로그를 확인할 수 있습니다.

## 가져오기

![이미지 등록](/img/screens/admin-image-import.png)

**이미지 등록** 기능은 레지스트리에 이미 존재하는 이미지를 플랫폼에 등록합니다. 등록 시 이미지 참조 경로, 표시 이름, CUDA 버전, 대상 GPU 모델을 설정합니다.

이미지가 실제로 정상 작동하기 위해서는 다음 두 가지 조건이 충족되어야 합니다.

- **노드가 해당 이미지를 풀(Pull)할 수 있어야 합니다.** 프라이빗 레지스트리를 사용하는 경우 노드별 신뢰 설정이 필요하며([클러스터 구축 → 로컬 레지스트리](../cluster-setup.md#local-registry-optional)), 멀티 클러스터 환경에서는 *모든* 클러스터에서 해당 레지스트리에 접근할 수 있어야 합니다.
- **CUDA 버전 정보가 정확해야 합니다.** 세션 생성 마법사는 설정된 CUDA 버전을 기준으로 필터링을 수행합니다. 예를 들어 CUDA 12.4로 빌드된 이미지의 버전을 12.8로 작성하더라도 Blackwell 카드에서 정상 작동하지 않으며, 이 경우 오류 감지가 지연되어 원인을 파악하기 더욱 어려워집니다.

## 빌드

![빌드 탭](/img/screens/admin-image-build.png)

**빌드** 탭에서는 플랫폼을 통해 실행된 이미지 빌드 프로세스의 진행 상태(`queued → building → pushing → scanning → succeeded`)와 각 단계별 로그를 실시간으로 추적할 수 있습니다.

이미지 빌드는 API(`POST /api/v1/image-builds`, 인라인 Dockerfile 또는 공개 Git 저장소 지정)를 통해서만 시작할 수 있으며, 현재 콘솔 UI에서는 별도의 빌드 시작 폼을 제공하지 않습니다. 또한 헬름 차트의 `operator.kanikoImage` 설정이 필수이며, 해당 값이 누락된 경우 오퍼레이터가 빌드 요청을 즉시 실패 처리합니다. 정상적으로 완료된 빌드 결과물은 `api.buildRegistry`에 푸시된 후 자동으로 등록됩니다.

사용자가 직접 가져오거나 빌드한 이미지는 해당 사용자에게만 노출되며(사용자당 최대 20개), 마법사 목록에서 **내 이미지** 태그가 표시됩니다.

## 시드 이미지

`api.seedSessionImages` 옵션이 활성화된 경우(기본값), 시스템 시작 시 CUDA 12.4/12.5 계열 및 Blackwell 12.8/12.9 계열용 `boanlab/gshare-session` 이미지가 카탈로그에 기본(시드)으로 등록됩니다. 단, 해당 태그 이미지는 릴리스 배포 워크플로가 정상 완료된 이후에만 Docker Hub에 생성되어 이용 가능합니다.

Blackwell GPU 플릿 환경에서는 CUDA 12.8 이상 계열이 필수입니다. 호환되지 않는 이전 버전의 이미지를 사용하는 경우 세션 시작 전에 `incompatible_image` 오류와 함께 차단됩니다. 이는 컨테이너가 생성된 후 GPU를 인식하지 못하는 문제를 사전에 방지하기 위한 정상적인 동작입니다.

## 카탈로그 최소화 유지

등록된 이미지가 늘어날수록 사용자의 선택 복잡도가 증가하며, 이미지를 다운로드받는 모든 노드에 5–15 GiB의 디스크 용량이 추가로 소모됩니다. 따라서 프레임워크 세대별로 수많은 파생 이미지를 생성하기보다는 잘 관리된 대표 이미지 하나를 유지하는 것이 권장됩니다. 특수한 환경이 필요한 경우 사용자가 직접 빌드하여 사용하도록 안내하세요.
