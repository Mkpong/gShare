# 자원 정책

**자원 정책**은 특정 테넌트(사용자, 부서, 조직)가 동시에 점유할 수 있는 자원의 상한을 정의합니다. 크레딧이 '자원 구매 가능 여부'를 결정한다면, 자원 정책은 '구매 자격과 별개로 실제 할당받을 수 있는 자원의 최대 한도'를 제어합니다.

![자원 정책](/img/screens/admin-policies.png)

## 정책 적용 순서: 상위 세부 설정 우선 적용

```
사용자  →  부서  →  조직  →  전역
```

정책은 **항목별(Field-level)**로 적용됩니다. 각 제약 항목마다 가장 구체적인 범주의 설정값(사용자 단위 설정)이 우선 적용되며, 해당 항목이 비어 있는(Null) 경우 하위 범위(부서 → 조직 → 전역)의 설정을 상속받습니다. 예를 들어 VRAM 항목만 설정된 사용자 정책의 경우, VRAM 한도만 사용자 정책을 따르고 나머지 제한 항목은 부서·조직·전역 정책의 설정값을 그대로 승계합니다. 마이페이지에서 각 지표 항목의 정책 출처 범위를 확인할 수 있습니다.

모든 제약 항목이 정의된 **전역(Global)** 정책을 기본 베이스로 구성하는 것을 권장합니다. 상위 정책(사용자/부서/조직)에서는 실제로 변경이 필요한 항목만 개별적으로 설정하여 관리할 수 있습니다.

## 정책 설정 항목

![새 정책](/img/screens/admin-policy-new.png)

| 항목 | 제약 대상 및 설명 |
|---|---|
| **최대 동시 실행** | 실행 중, 일시정지, 대기 상태인 세션 수의 총합 |
| **최대 대기** | 대기열에서 동시 대기 가능한 세션 수 |
| **VRAM / GPU 코어** | 해당 테넌트가 점유하는 전체 GPU 세션의 자원 합계 |
| **CPU / 메모리 / 디스크** | 전체 세션이 점유하는 호스트 자원의 합계 |
| **스토리지** | 전체 볼륨의 용량(쿼터) 합계 |
| **최대 실행 시간** | 단일 세션의 최대 허용 실행 시간 (초과 시 세션 자동 종료) |
| **유휴 시간** | 세션 미사용(Idle) 상태 허용 시간 (초과 시 GPU 세션이 **일시정지**되고 GPU 자원이 반환됨) |
| **CPU 세션 한도** | 무료 CPU 세션에 별도로 적용되는 독립적 자원 한도 |
| **공용 풀 사용** | 전용 [풀](./node-pools.md) 자원이 고갈되었을 때 공용 노드로 자원을 오버플로 할당할 수 있는지 여부 |
| **권한 있는 세션** | 컨테이너를 Root 권한으로 실행 허용할지 여부 |

설정값이 비어 있는 항목은 제약 없음(무제한)으로 처리됩니다.

### 과부하 클러스터 환경의 필수 추천 설정

- **유휴 제한 시간 (Idle Timeout)**: 방치된 세션이 GPU 자원을 장시간 점유하는 것을 방지합니다. 기본 1시간 설정을 권장하며, 제한 시간 도달 시 세션이 강제 종료되는 것이 아니라 일시정지 상태로 전환되므로 사용자는 자원 재개만으로 작업을 이어갈 수 있습니다.
- **최대 동시 실행 세션 수**: 단일 사용자가 다수의 세션을 동시에 생성하여 클러스터 전체 자원을 독점하는 현상을 방지합니다.

## 자원 증액 요청 {#자원-증액-요청}

![들어온 요청](/img/screens/admin-quota-requests.png)

할당 한도를 초과한 사용자는 마이페이지에서 **자원 증액 요청**을 제출할 수 있습니다. 제출된 요청은 관리자 콘솔의 **증액 요청** 탭에 수신되며, 변경 요청 항목, 현재 설정값, 신청 사유가 함께 표시됩니다.

**증액 요청을 승인하면 해당 사용자에게만 적용되는 개별 사용자 정책이 신규 생성(또는 기존 정책 갱신)되어 적용됩니다.** 항목별 상속 규칙에 따라 승인된 요청 항목 외 나머지 제한 지표는 기존 부서·조직·전역 정책의 설정을 계속 유지합니다. 운영 효율성을 위해 다음 모범 사례를 따르는 것이 좋습니다.

- 승인 시 요청된 특정 항목만 변경하여 사용자 개인 정책의 복잡도를 최소화하세요.
- 동일한 자원 부족 현상이 팀/부서 단위로 발생하는 경우, 개별 승인보다는 **부서 정책** 전체를 수정하는 것이 관리적 측면에서 훨씬 효율적입니다.

요청을 반려할 경우 신청자에게 전달할 반려 사유를 입력해야 합니다. 승인 및 반려 내역은 모두 감사 로그(Audit Log)에 기록되며 해당 사용자에게 알림이 발송됩니다.

:::tip 크레딧 부족과 쿼터 한도 구분
사용자 작업 실패 원인이 *크레딧 부족*인 경우, 자원 증액 요청이 아닌 [크레딧 요청](./credits-requests.md) 프로세스를 진행해야 합니다. 쿼터 한도를 증액하더라도 크레딧 잔액은 증가하지 않습니다.
:::
