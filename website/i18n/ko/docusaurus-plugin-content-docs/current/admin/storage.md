# 스토리지

여기에는 두 가지가 있습니다. 사용자 볼륨을 받치는 **풀**, 그리고 **볼륨** 자체.

## 스토리지 풀

![스토리지 풀](/img/screens/admin-storage-pools.png)

풀은 노드 역할에서 추론하는 것이 아니라 등록하는 객체입니다. 서버가 있는 클러스터, 거기서
프로비저닝하는 StorageClass, 그리고 공유 범위(**모든** 클러스터 또는 **선택한** 클러스터).
**스토리지 풀** 탭이 그 목록이며, 대시보드의 스토리지 타일과 새 볼륨을 승인하는 용량 게이트 모두 이
목록을 읽습니다. 여기 등록되지 않은 서버는 계산에 들어가지 않습니다.

### 서버 등록하기

순서는 노드 라벨 → 드라이버 설치 → 풀 등록입니다.

1. 스토리지 노드에 `gshare.io/role=storage` 라벨을 답니다(`STORAGE_NODE`를 적어 두면 부트스트랩
   스크립트가 해 줍니다). 그러면 [노드](./nodes.md)에 *Storage* 역할로 나타납니다.
2. CSI 드라이버를 설치하고 오퍼레이터에 그 StorageClass를 줍니다(`operator.volumeStorageClass`).
   [운영 → 스토리지](../operations/storage.md) 참고.
3. **풀 등록**:

![풀 등록](/img/screens/admin-storage-pool-new.png)

| 항목 | 의미 |
|---|---|
| **풀 이름** | 항상 연결한 노드의 **호스트명** — 클러스터에 노드로 보이지 않는 서버일 때만 직접 적음 |
| **클러스터** | 서버가 속한 클러스터. 등록 후에는 고정 |
| **StorageClass** | 이 서버에서 프로비저닝하는 클래스 — 오퍼레이터에 준 것과 같은 이름 |
| **스토리지 노드** | 선택. 라벨을 단 노드. 그 디스크가 대체 용량이 됨 |
| **수동 용량 (GB)** | 드라이버가 용량을 발행할 때까지 쓰는 실제 풀 크기 |
| **공유 범위** | *전체 클러스터* — 모든 클러스터가 여기에 볼륨을 둘 수 있음. *선택* — 이 클러스터 외에 허용할 클러스터를 체크 |

**편집**은 클러스터 외 모든 것을 바꾸고, **삭제**(이름 입력 확인)는 서버를 계산에서 뺍니다. 이미 그
위에 있는 볼륨은 StorageClass를 통해 계속 동작하고, 스토리지 자체는 건드리지 않습니다.

![풀 제거](/img/screens/admin-storage-pool-delete.png)

### 용량 값의 출처

각 행에 값과 출처가 표시되며, 우선순위는 다음과 같습니다.

1. **csi** — 드라이버의 `GetCapacity`. `CSIStorageCapacity`로 발행되고 오퍼레이터가 읽습니다. 유일한
   자동 소스입니다.
2. **manual** — 풀에 적어 둔 값. 드라이버가 아무것도 발행하지 않을 때 설정합니다.
3. **node disk** — 스토리지 노드의 시스템 드라이브. 대용임을 표시합니다.

서버가 여러 대면 풀도 여러 개입니다. 볼륨은 정확히 하나에 존재하므로 상한은 합계가 아니라 사용
가능한 **가장 큰** 풀입니다. 드라이버 플래그, NFS 전제 조건, 두 번째 클러스터 연결 같은 운영자
관점은 [운영 → 스토리지](../operations/storage.md)에 있습니다.

## 볼륨

![전체 볼륨](/img/screens/admin-volumes.png)

플릿의 모든 볼륨을 소유자·범위·종류·접근 모드·사용량 대비 쿼터, 그리고 **데이터가 있는 곳** — 그
볼륨을 담고 있는 스토리지 풀(과 클러스터) — 과 함께 보여 줍니다. 아직 어떤 세션도 마운트하지 않은
볼륨은 클레임이 없어 위치도 없으며, 첫 마운트가 만들기 전까지 *아직 미생성*으로 표시됩니다.
스토리지 서버가 여럿일 때 어느 볼륨(과 사용자)이 어느 서버에 의존하는지 알려 주는 열입니다.

| 작업 | 효과 |
|---|---|
| **쿼터 변경** | 볼륨 쿼터를 올림 — 소유자의 스토리지 한도 안에서. 그 이상은 먼저 [정책](./resources-policies.md)을 올리세요 |
| **잠금** | 실행 중 세션은 두고 새 마운트만 거부 |
| **삭제** | 일반 삭제. 마운트한 세션이 있으면 거부 |
| **강제 삭제** | 쥐고 있는 세션을 종료한 뒤 삭제 |

![강제 삭제](/img/screens/admin-volume-force-delete.png)

강제 삭제는 콘솔에서 가장 날카로운 도구입니다. 볼륨을 지우려고 남의 실행 중 세션을 끝냅니다.
대화 상자가 소유자를 명시하고 그렇게 말하며, 감사 항목에 어느 세션을 끊었는지 남습니다. 스토리지
서버가 정말 꽉 찼고 소유자와 연락이 되지 않을 때만 쓰세요.

## 공간이 부족할 때

풀이 차면 다음 순서가 유용합니다.

1. **큰 것을 찾습니다** — 사용량으로 정렬. 잊고 둔 임시 볼륨 몇 개가 원인인 경우가 대부분입니다.
2. **소유자에게 묻습니다** — 관리자가 지우는 것보다 소유자가 지우는 편이 언제나 낫고, 콘솔이 누구인지
   정확히 알려 줍니다.
3. 기다리는 동안 **삭제가 아니라 잠금**을 걸어 두세요. 파괴하지 않으면서 더 커지는 것만 막습니다.
4. 같은 청소를 반복하지 않으려면 [정책](./resources-policies.md)의 스토리지 한도를 조이세요.

삭제된 볼륨은 `api.volumeReclaimGraceHours`(기본 24시간) 후 회수됩니다. 그 안에는 운영자가 데이터를
복구할 수 있습니다.
